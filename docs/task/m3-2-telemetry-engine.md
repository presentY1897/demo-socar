# M3-2 — 텔레메트리 모의 엔진

- 마일스톤: M3 (운영 백오피스 재설계) · 규모 M
- 상태: ☑ 완료
- 의존: M3-1

## 목적

피드백 #5 "스마트 차량의 내부 센서 정보를 어떻게 뿌릴 건지". 실차 없이 그럴듯한 센서 값을 만드는 모의 엔진. **조회 시점 계산 + SSE 주기 갱신** 방식(Q4 기본값 — 백그라운드 워커 없음, 무료 티어 CPU 고려).

## 작업 내용

- [x] 모의 규칙 (순수 함수로 분리, 단위 테스트 대상):
  - 대여 중(IN_USE): 마지막 갱신 이후 경과 시간 × 15~35km/h(기존 반납 모의와 동일 분포) → 위치는 존→반납 예정지 방향 보간, odometer 증가, 연료 100km당 ~12% 감소(EV는 완속 기준)
  - 탁송 중(EN_ROUTE 작업): A* 경로 위 보간
  - 대기 중: 변화 없음 (문 잠금/시동은 스마트키 조작 값 유지)
  - 반납/작업 완료 시: 그 시점 값으로 스냅샷 확정 저장
- [x] 조회 경로: 텔레메트리를 읽는 모든 API가 "저장값 + 경과 시간 계산"으로 현재값 산출, 일정 간격(60초) 넘으면 저장값 갱신(write-through)
- [x] SSE: 기존 `/metrics/vehicles/live` 채널에 텔레메트리 필드 포함, 5초 틱

### 설계 메모

- **난수를 쓰지 않는다.** 속도(15~35km/h)와 왕복 반환점의 방향을 차량 id에서 결정적으로 뽑는다. 그래서 ① 같은 차를 두 번 조회해도 값이 뒤로 가지 않고 ② 중간에 몇 번 write-through 했든 총 주행거리가 `이용 시간 × 속도`로 같으며 ③ 단위 테스트가 시각만 바꿔 넣어 기대값을 그대로 계산할 수 있다. `Rental.distanceKm`(반납 정산)도 같은 함수(`mockDrivenKm`)를 쓰므로 계기판과 청구가 어긋나지 않는다
- **연료 감소율**: 내연 12% / 하이브리드 9% / EV 18% (100km당). EV는 같은 거리에서 더 크게 준다 — 주행 가능 거리가 짧다는 감각. 하한 5%를 둔다(모의 엔진에 주유·충전이 없어 0%인 차가 계속 달리는 것보다 낫다)
- **왕복 보간**: 출발·도착이 같아 그대로 보간하면 차가 붙박이가 된다. 차량마다 고정된 방향으로 `예상 주행거리 ÷ 2`만큼 떨어진 **가상 반환점**을 잡고 전반부에 나갔다가 후반부에 돌아온다
- **탁송 보간**: 그래프 A*가 경로 좌표열이 아니라 거리·시간만 돌려주므로 출발↔도착을 직선 보간하되 **페이스를 A* 추정 시간에 맞춘다**. 경로가 멀수록 오래 걸리는 건 그대로 재현되고, 좌표열을 얻자고 A*를 뜯어 고치는 값은 데모에 비해 크다
- **스냅샷 확정(`freeze`)은 진행 상태를 DB에서 다시 보지 않는다.** 확정은 언제나 "이동이 끝난 직후"에 불리고 그때는 이미 예약이 COMPLETED·작업이 DONE이라 DB만 봐서는 "방금까지 달리고 있었다"를 알 수 없다 — 호출자가 `drivenSince`로 알려 준다
- **상태 4종(대기/운행/탁송/정비)**은 `packages/shared`의 `opsVehicleStateSchema` + `OPS_VEHICLE_STATE_META`가 단일 소스. SSE·`/ops/fleet`·백오피스 화면이 같은 값과 라벨을 본다 (기존 SSE의 `AVAILABLE`은 `IDLE`로 이름이 바뀌었고 `IN_TRANSIT`이 늘었다 — 기존 대시보드도 함께 맞췄다)
