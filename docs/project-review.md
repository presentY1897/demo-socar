## 2. 지금까지 한 것

실제 진행 순서대로 4단계. 각 항목은 main에 커밋·배포 완료된 상태다. 항목별 상세 스펙은 §3.

### P1. 기반 구축과 도메인 구현

- **모노레포 스캐폴드** — pnpm + Turborepo, NestJS 11 + Prisma(API), Next.js 15 PWA(웹), zod 공유 패키지
- **도메인 API 전체 + 전국 도로망 A\* 파이프라인** — 예약 동시성(EXCLUDE USING GIST, ADR-001), 결제 멱등성(ADR-002), 대여~반납 상태 머신, OSM → 경량 그래프 전처리(ADR-004)
- **웹 프론트 전체 화면** — 개인 이용자 / 법인 임직원 / 배차 담당 / 운영 어드민 4개 역할 화면, PWA
- **마이그레이션 · 통합테스트 · 배포 설정 · 문서**
- **법인 배차를 쏘카 FMS 모델로 확장** — 사실 확인 요구("실제 기능이야?") 후 재설계: 전용 차량 우선 + 공유존 폴백, 추천 근거 + 담당자 승인(ADR-003)

### P2. 클라우드 배포

- **Vercel(웹) + Render(API) + Neon(DB) 배포 완료** — timestamptz 전환, 헬스체크 공개, A* 그래프 프로덕션 로드 확인
- **콜드 스타트 웜업 게이트** — Render 슬립 대응: 접속 시 진행 오버레이 + 기상 후 SWR 캐시 재검증

### P3. 실물 앱 정합화 (전면 재수정 요구 반영)

- **시간 우선 탐색 + 10분 단위 예약** — 이용 시간을 먼저 정하고 그 시간의 가용 존/차량 + 예상 요금 탐색, 최소 30분
- **요금 정합화** — 주행요금 30km 면제 · EV 전면 무료, 면책상품 3종(자기부담금 0/30/70만원)
- **예약 변경 · 이용 중 연장** — 차액 결제/크레딧 환급, 뒤 예약 충돌 시 409 (동시성 제어 어필 포인트)
- **반납 자동 정산** — 원클릭 반납 → 모의 텔레메트리로 주행거리 자동 확정 → 정산
- **편도 예약** — 차량 위치를 예약 체인의 시간 함수로 계산(ADR-005), 하버사인 기반 편도 수수료
- **부름(탁송) 수령** — A* 운전 속도 탁송 시간 기반 가용성(ADR-006), 검색 결과를 "바로 픽업 / 부름으로 가져와 이용"으로 구분

### P4. 실데이터 전환과 품질

- **존을 실제 주차장 데이터로 교체** — 전국주차장정보표준데이터(공공데이터포털) 27곳 + OSM 보충 3곳, 이름·주소·면수 실데이터
- **시드 버전 마커** — SEED_VERSION 증가만으로 배포 시 자동 1회 재시드, 수동 개입 제거
- **지도 줌 레벨 기반 존 클러스터링** — 가장 최근 커밋

## 3. 현재 구현 스펙 (As-Built)

코드 기준으로 정리한 실제 스펙 — 프론트 페이지 8개, API 엔드포인트 27개, 도메인 모델 13개.
"이 화면/기능이 왜 있지, 빼자, 다르게 가자" 수준의 피드백을 받는 게 목적.

### 3.1 프론트엔드 — 페이지 구성 (Next.js App Router)

| 경로 | 대상 | 화면과 기능 |
|---|---|---|
| `/login` | 공통 | 데모 계정 4종 로그인 (JWT 발급 후 역할별 홈으로 이동) |
| `/` | 개인 이용자 | 홈 = 시간 우선 탐색. 상단 이용시간 바(10분 단위 픽커, 기본 지금+30분~2시간) → Leaflet 지도에 존 표시(줌 아웃 시 클러스터링) → 존 클릭 시 바텀시트: 그 시간 가용 차량 목록 + 차량별 예상 요금, **"바로 픽업" / "부름으로 가져와 이용"** 구분 표기. 데이터: `GET /zones`, `GET /zones/:id` |
| `/book/[vehicleId]` | 개인 이용자 | 예약 확정 화면. 시간은 홈에서 쿼리로 받아 상단 표시(수정 = 홈 복귀). 면책상품 3종 선택(자기부담금 0/30/70만원) · 편도 반납존 선택 + 수수료 표시 · 부름 수령지 지도 핀 선택(편도와 배타) · 쿠폰/크레딧 적용 · 모의 카드 입력(`0000` 끝자리는 승인 거절 데모) → 견적 확인 → 결제. 데이터: `POST /reservations/quote` → `POST /reservations` (멱등성 키 포함) |
| `/reservations` | 개인 이용자 | 내 예약 목록 — 상태(확정/이용 중/완료/취소), 편도·부름 표기 |
| `/reservations/[id]` | 개인 이용자 | 예약 상세 = 라이프사이클 허브. 이용 전: **시간 변경**(차액 결제/환급)·취소 / 시작: 대여 개시 / 이용 중: **반납 연장**(뒤 예약 충돌 시 409 안내) / **원클릭 반납** → 주행거리 자동 확정 → 정산 내역(주행요금·편도 수수료·지연료) 표시 |
| `/office` | 법인 임직원 + 배차 담당 | 역할에 따라 두 모드. **임직원**: 배차 요청 생성(목적·희망 시간) + 내 요청 상태 확인. **담당자**: 요청별 후보 차량 추천을 근거와 함께 검토 — 전용/공유 여부·비용, 오피스→존 A* 도보 시간, 직전 예약 반납 버퍼, 최근 30일 지연 반납 리스크 — 승인(→ 예약 자동 생성) 또는 반려(사유 입력) |
| `/office/board` | 배차 담당 | 차량 × 시간 타임라인 보드 — 날짜별 예약 점유 현황 한눈에 |
| `/dashboard` | 운영 어드민 | 매출·예약 수·가동률·지연반납률 요약 + 일별 차트(Recharts) + **SSE 실시간 차량 현황** |

**공용 컴포넌트**

- `AppShell` — 역할별 내비게이션 셸 (개인/법인/어드민 메뉴 분기)
- `ZoneMap` — Leaflet 지도 + 줌 레벨 기반 존 클러스터링
- `TimeRangePicker` — 10분 단위 시작~반납 시각 픽커 (홈·변경·연장에서 재사용)
- `DeliveryMapPicker` — 부름 수령지 지도 핀 선택 (반경 5km 제한)
- `ServerWarmup` — 콜드 스타트 게이트: /health 확인 → 진행 오버레이 → 기상 시 SWR 재검증
- `RegisterSW` — PWA 서비스워커 등록

### 3.2 백엔드 — API 엔드포인트 (NestJS, 도메인별 9개 모듈)

**인증 · 내 정보**

| 엔드포인트 | 기능 |
|---|---|
| `POST /auth/login` | 이메일/비밀번호 → JWT 발급 |
| `GET /auth/me` | 세션 사용자 정보 (역할 포함) |
| `GET /me/coupons` | 보유 쿠폰 목록 |
| `GET /me/credit` | 크레딧 잔액 (원장 합산) |

**존 · 차량 탐색**

| 엔드포인트 | 기능 |
|---|---|
| `GET /zones?startAt&endAt` | 존 목록 — 구간 지정 시 존별 "그 시간 가용 차량 수" 포함 |
| `GET /zones/:id?startAt&endAt` | 존 상세 — 구간 가용 차량만 + 차량별 예상 요금. 가용 판정은 차량의 시간별 위치 체인(편도 반영) 기준, 바로 픽업/부름 구분 포함 |
| `GET /zones/:id/return-zones` | 편도 반납 가능한 존 목록 (같은 region 공유존) |
| `GET /vehicles/:id` | 차량 상세 (모델·연료·요금제·현재 존) |
| `GET /vehicles/:id/availability?date` | 날짜별 예약 점유(busy) 슬롯 — 시간 변경/연장 UI용 |

**예약** (동시성 제어 ADR-001 · 결제 멱등성 ADR-002)

| 엔드포인트 | 기능 |
|---|---|
| `POST /reservations/quote` | 견적 — 시간·면책·편도 수수료·부름·쿠폰·크레딧 반영한 금액 분해 |
| `POST /reservations` | 예약 생성 + 모의 결제. 트랜잭션 사전검사 + `EXCLUDE USING GIST` 이중 방어, 멱등성 키로 중복 결제 차단. 편도(`returnZoneId`)/부름(`delivery` 좌표+라벨)은 zod 스키마에서 상호 배타 검증 |
| `PATCH /reservations/:id` | 이용 전 시간 변경 — 재견적 후 차액 양수면 추가 결제, 음수면 크레딧 환급 |
| `GET /reservations/mine` | 내 예약 목록 |
| `GET /reservations/:id` | 예약 상세 (결제·대여 상태 포함) |
| `POST /reservations/:id/cancel` | 취소 + 환불 처리 |

**대여 라이프사이클**

| 엔드포인트 | 기능 |
|---|---|
| `POST /rentals/start` | 대여 개시 (예약 → IN_USE) |
| `POST /rentals/:id/extend` | 이용 중 연장 — 뒤 예약과 충돌 시 409, 연장분 차액 결제 (전용 차량은 0원) |
| `POST /rentals/:id/return` | 원클릭 반납 — 모의 텔레메트리(경과시간×15~35km/h)로 주행거리 자동 확정 → 즉시 정산 호출 |
| `POST /rentals/:id/settle` | 정산 (멱등 재시도 진입점) — 주행요금 30km 면제·EV 무료, 지연료, 편도면 차량 존 이동 확정 |

**법인 배차** (추천 + 승인, ADR-003)

| 엔드포인트 | 기능 |
|---|---|
| `POST /dispatch/requests` | 임직원 배차 요청 → 후보 차량 스코어링(전용 우선 + 공유존 폴백) 자동 생성 |
| `GET /dispatch/requests` | 요청 목록 (임직원: 내 것 / 담당자: 법인 전체) |
| `GET /dispatch/requests/:id` | 요청 상세 — 후보별 점수·근거(도보 시간, 버퍼, 지연 리스크) |
| `POST /dispatch/requests/:id/approve` | 담당자 승인 — 동시성 제어를 거쳐 예약 생성 |
| `POST /dispatch/requests/:id/reject` | 반려 (사유 기록) |
| `GET /dispatch/board?date` | 차량 × 시간 타임라인 보드 데이터 |

**운영 지표 · 헬스**

| 엔드포인트 | 기능 |
|---|---|
| `GET /metrics/summary?days` | 매출·예약·가동률·지연반납률 요약 (SQL 집계) |
| `GET /metrics/daily?days` | 일별 시계열 (차트용) |
| `SSE /metrics/vehicles/live` | 실시간 차량 현황 스트림 |
| `GET /health` | 헬스체크 (웜업 게이트·킵얼라이브가 사용) |

### 3.3 공유 패키지 (packages/shared) — API·웹이 같은 계약을 공유

- **zod 스키마** (auth · reservation · dispatch) — API 입력 검증과 웹 폼 검증이 동일 소스. 예: 예약 생성 스키마가 "부름과 편도 동시 사용 불가", "10분 정렬·최소 30분" 규칙을 양쪽에서 강제
- **요금 엔진** (순수 함수) — `quote()`: 10분 슬롯 단가(시간당/6)·주중주말·면책·편도 수수료·쿠폰/크레딧 적용 순서 / `settle()`: 주행요금(30km 면제, EV 무료)·지연료. 단위 테스트 34케이스의 대상
- **geo** — 하버사인 거리(편도 수수료·부름 반경 판정), 좌표 유틸

### 3.4 데이터 모델 (Prisma, PostgreSQL)

| 모델 | 역할 · 핵심 제약 |
|---|---|
| User / Corporation | 4역할(개인·법인임직원·법인배차담당·운영어드민), 법인 소속 관계 |
| Zone / Vehicle / PricingPlan | 존(실제 주차장 30곳) · 차량(연료 타입, 전용/공유, 물리 위치 존) · 요금제 |
| Reservation | 예약 — `EXCLUDE USING GIST`로 같은 차량 시간 겹침을 DB 레벨 차단. `returnZoneId`(편도) · 부름 수령 좌표 · 면책 티어 |
| Rental | 대여 상태 머신 (개시→이용 중→반납→정산), 주행거리·지연 기록 |
| Payment | 결제 상태 머신 + 멱등성 키 유니크 — 재시도해도 중복 결제 없음 |
| Coupon / CreditLedger | 쿠폰 · 크레딧 원장(적립/사용/환급 사유별 기록, 잔액은 합산) |
| DispatchRequest / DispatchCandidate | 배차 요청과 후보 — 점수·근거(도보 시간, 버퍼, 지연 리스크)를 행으로 보존해 "왜 이 추천인지" 재현 가능 |
| SeedMeta | 시드 버전 마커 — 배포 시 1회 자동 재시드 판단 |

## 4. 확정된 결정사항

이미 합의되어 문서화까지 끝난 결정들. 뒤집을 항목이 있으면 피드백.

### 핵심 설계 (ADR 6건)

### 5.3 M2 — 핸들러(운송기사) 시스템 (규모 M)

실제 쏘카에서 부름 배달·회수·재배치를 수행하는 '쏘카 핸들러' 역할. 부름 기능은 이미 있으므로 그 작업을 사람이 처리하는 화면을 만든다 — 배달앱 기사 화면 문법.

**신규 도메인 (마이그레이션 1건)**

- User.role에 `HANDLER` 추가 + 데모 계정 `handler@demo.mocar.kr` (데모 계정 5종이 됨)
- `HandlerTask` — type(DELIVERY 부름 배달 / RETRIEVE 회수 / REPOSITION 재배치) · status(대기→배정→이동 중→완료) · 대상 차량/예약 · 출발 존/목적지 좌표 · 배정 핸들러 · 기한 · 완료 사진/메모

**연계 규칙**

- 부름 예약 결제 완료 → DELIVERY 작업 자동 생성 (기한 = 이용 시작 − 리드타임 60분)
- 부름 이용 반납 → RETRIEVE(제자리 회수) 작업 자동 생성
- 백오피스(M3)에서 REPOSITION 수동 생성·배정

**API**

| 엔드포인트 | 기능 |
|---|---|
| `GET /handler/tasks` | 내 작업 큐 (오늘/예정, 시간순) |
| `POST /handler/tasks/:id/accept · start · complete` | 상태 전환 — 완료 시 인계 사진+메모 필수 |
| `GET /ops/tasks` · `POST /ops/tasks/:id/assign` | 백오피스 배정 — 핸들러 현재 위치 기반 거리 추천 후보 포함 |

**웹**

- `/handler` — 오늘 작업 카드 큐, 작업 상세(픽업 존→목적지, A* 예상 이동 시간, 지도), 상태 전환 버튼, 완료 촬영

- **Export** — 모든 리포트·목록(차량/예약/작업/유저 리스크)에 `format=csv|json` 다운로드 (Content-Disposition, 적용 중인 필터 조건 그대로 반영)

### 5.5b M5 — MOCAR 비즈니스: 법인 플릿/리스 관리 서비스 분리 (규모 L, 2·3차 피드백)

법인 기능을 소비자 앱의 부속이 아니라 **"법인 차량 리스까지 관리하는 분리된 B2B 서비스"**로 재구성한다 (3차 피드백). 실제 쏘카 비즈니스/FMS 라인업과도 평행한 프레이밍.

- **서비스 분리** — 웹 `/biz` 라우트 그룹 + 전용 BizShell(기존 /office → /biz/dispatch 이동), API는 `apps/api/src/biz/` 바운디드 컨텍스트로 재배치. "별도 앱으로 추출한다면 여기서 자른다"는 경계를 의존 방향까지 정리해 ADR-010에 기록
- **리스 도메인** — `LeaseContract`(법인↔MOCAR 계약: 월 리스료·기간·상태). **기존 FMS 전용 차량 = 리스 계약으로 개념 통합**(백필). M3 `VehicleFinance`(MOCAR 원가 관점)와 구분되며, 리스료는 M3 회계에서 MOCAR 매출로 합산 가능
- **플릿 관리** — `/biz/fleet`: 법인 차량의 계약 만기 D-day·월 비용·이용률·운행일지, **리스 연장/해지 요청 워크플로**(법인 요청 → 운영 어드민 승인, 해지 시 회수 작업 생성으로 M2 연계)
- **등급 권한** — `VIEWER`(조회) → `REQUESTER`(+요청) → `APPROVER`(+승인·보드) → `MANAGER`(+멤버 등급·플릿/리스 관리). 권한 매핑은 shared 단일 소스(API 가드 = 웹 분기), MANAGER 전용 멤버 관리(`/biz/members`), 자기 강등 방지
- 데모 계정 `viewer@demo.mocar.kr` 추가 (총 6종)
- 작업 6개: [M5-1](task/m5-1-corp-grade-domain.md) 도메인 → [M5-2](task/m5-2-biz-separation.md) 서비스 분리 → [M5-3](task/m5-3-permission-guards.md) 가드/API → [M5-4](task/m5-4-grade-ui.md) 등급 UI → [M5-5](task/m5-5-fleet-lease-mgmt.md) 플릿/리스 → [M5-6](task/m5-6-verify-deploy.md) 검증·배포

### 5.6 구현 순서 제안

**M0 → M1 → M2 → M3 → M4 → M5.**
근거: ① M0-2(테스트 기반)가 모든 프론트 작업의 선행 ② M1이 이용자 여정의 구멍(빌리는 경험)을 막는 게 먼저 ③ M2가 만드는 작업 데이터가 M3 백오피스의 재료 ④ M3 화면이 서야 M4 리포트가 의미 있음. **M5는 독립적이라 원하면 앞으로 당길 수 있음**(예: M1 직후). 각 마일스톤 완료 시 배포 + 문서 갱신 + 리뷰 후 다음 진행.

### 5.7 보류 (기능 확장 후)
