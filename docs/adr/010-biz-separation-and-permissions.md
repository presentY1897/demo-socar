# ADR-010. MOCAR 비즈니스 — 법인 서비스 분리 경계와 권한 모델

## 상황

3차 피드백의 요구는 두 겹이었다. "법인 차량의 **리스도 관리**하는 서비스"로 프레이밍할 것,
그리고 그 서비스를 "**분리해서 처리 가능하게**" 구성할 것.

M5 이전의 법인 기능은 소비자 앱에 섞인 부속이었다:

- 배차 화면이 `/office`에 있었고 소비자 셸(AppShell) 안에서 그려졌다
- API `dispatch` 모듈이 `ReservationsService`를 직접 import 했다
- 권한은 전역 역할 두 개(`CORP_MEMBER` / `CORP_ADMIN`)로만 갈렸고,
  "조회만 되는 사람"이나 "승인만 하는 사람"을 표현할 자리가 없었다
- 법인 전용 차량은 `Vehicle.corporationId`가 붙은 차량일 뿐, **계약**이라는 개념이 없었다

결정해야 했던 것:

1. 분리 경계를 **어디에** 긋고, 실제로 떼어낼 때 **무엇을 바꾸면** 되는가
2. 이미 남아 있는 결합을 어떻게 다룰 것인가 — 지우지 못한다면 어떻게 관리할 것인가
3. 권한의 근거를 **전역 역할**로 둘 것인가 **법인 내 등급**으로 둘 것인가
4. 계약(리스)의 소유권이 법인에 있는가 MOCAR에 있는가

## 결정 1 — `/biz`를 바운디드 컨텍스트로 자르고, 나가는 길을 포트 하나로 모은다

경계는 세 층에서 같은 선을 긋는다.

| 층 | 경계 | 내용 |
|---|---|---|
| URL | `/biz/*` | 소비자 API와 이름공간이 겹치지 않는다. 구 `/dispatch/*`는 폐기 |
| API | `apps/api/src/biz/` | `dispatch` · `members` · `fleet`(+`leases`) 서브모듈, 루트는 `biz.module.ts` |
| 웹 | `app/biz/` + `BizShell` | 소비자 `AppShell`과 다른 셸·내비·브랜딩. `AppShell`이 경로로 한 번 가른다 |

핵심은 **의존 방향을 한 방향으로 고정**한 것이다. biz는 소비자 도메인의 서비스를
직접 부르지 않고, 나가는 호출을 포트 하나에 모았다.

```
   biz 컨텍스트                                  소비자 도메인
  ┌───────────────────────────────┐            ┌──────────────────────┐
  │ dispatch.service              │            │ ReservationsService  │
  │ fleet.service · leases.service│            │ ZonesService · ...   │
  │ members.service               │            └──────────▲───────────┘
  │            │                  │                       │
  │            ▼                  │                       │
  │  ports/reservation-booking    │  ← 인터페이스          │
  │  (RESERVATION_BOOKING 토큰)    │                       │
  └────────────┬──────────────────┘                       │
               │ DI                                       │
  ┌────────────▼──────────────────┐   in-process 호출     │
  │ adapters/reservations-booking │──────────────────────┘
  │ (biz 안에서 reservations를    │
  │  아는 **유일한** 파일)         │
  └───────────────────────────────┘
```

- `apps/api/src/biz/ports/reservation-booking.port.ts` — biz가 밖으로 나가는 유일한 창구.
  `BookingActor` / `BookingRequest` / `BookingResult`만 오간다 (Prisma 타입이 새지 않는다)
- `apps/api/src/biz/adapters/reservations-booking.adapter.ts` — 그 포트의 in-process 구현.
  biz 안에서 `ReservationsService`를 아는 파일은 여기 하나뿐이다

### 실제로 떼어낼 때 바꾸는 것

별도 앱/배포로 추출한다면 손대는 곳은 다음 다섯 군데다. **biz의 도메인 코드는 그대로 둔다.**

1. **어댑터 교체** — `ReservationsBookingAdapter`를 `POST /reservations` HTTP 클라이언트로.
   `dispatch.service`는 포트 타입만 알고 있어 한 줄도 바뀌지 않는다
2. **읽기 경로** — 아래 잔여 결합 표의 #1·#2·#7이 "차량 가용성/이용 이력 조회" API 호출로 바뀐다
   (지금은 공용 DB를 직접 읽는다)
3. **인증** — 토큰 발급자를 공유하거나(JWKS) biz 전용 세션을 세운다 (#5)
4. **웹** — `app/biz/` 라우트 그룹과 `BizShell`을 새 앱의 루트로 옮기고,
   `AppShell`의 `/biz` 분기 1줄과 `next.config` 리다이렉트를 걷어낸다 (#6)
5. **계약 쓰기** — `LeaseContract` 테이블의 소유권을 정한다 (#8, 결정 7 참고)

> 이 데모에서 실제로 서비스를 쪼개지는 **않는다**. 무료 티어 배포가 하나라 프로세스를 나누면
> 콜드 스타트가 두 배가 되고, 얻는 것은 없다. 이 ADR이 기록하는 것은 "지금 쪼개져 있다"가
> 아니라 **"쪼갤 때 무엇을 건드리면 되는지가 코드에서 보인다"**이다.

## 결정 2 — 잔여 결합은 지우는 대신 목록으로 들고 간다

경계를 그었다고 결합이 사라지지 않는다. 남은 것을 주석과 표에 적어 두고, 각 항목에
"추출 시 필요한 것"을 붙였다. 목록이 없으면 다음 사람은 코드를 다 읽고 나서야
무엇이 걸려 있는지 알게 된다.

## 결정 3 — 권한의 근거는 전역 역할이 아니라 법인 등급이다

`Role`(USER / CORP_MEMBER / CORP_ADMIN / OPS_ADMIN / HANDLER…)은 **서비스 전역에서 이 계정이
무엇인가**를 말한다. 인증·라우팅·소비자 기능의 노출이 여기에 걸린다.

`corpGrade`(VIEWER / REQUESTER / APPROVER / MANAGER)는 **한 법인 안에서 이 사람이 무엇을 할 수
있는가**를 말한다. 법인 소속이 아니면 값이 없다(`null`).

둘을 합치지 않은 이유는 하나다. **합치면 법인 안의 권한 변경이 전역 역할 변경이 된다.**
"이 임직원을 승인 담당으로 올린다"가 `Role`을 `CORP_ADMIN`으로 바꾸는 일이 되면,
그 계정은 법인 밖에서도 다른 계정이 되어 버린다. 등급은 법인이 자기 안에서 굴리는 값이고,
법인 관리자가 스스로 바꿀 수 있어야 하는 값이다. 전역 역할은 그럴 수 없다.

이 설계의 요점을 데모 계정 하나가 보여준다:

> **`approver@demo.mocar.kr`(정승인)은 `Role = CORP_MEMBER`(임직원)인데 배차를 승인한다.**
> 역할만 보면 평범한 임직원이고, 승인 권한은 오직 등급(`APPROVER`)에서 나온다.
> 통합 테스트가 승인 성공과 `role === 'CORP_MEMBER'`를 **같은 테스트 안에서** 단언한다
> (`test/biz-permissions.int-spec.ts`, `test/m5-e2e.int-spec.ts` ⑤).

### 등급 × 권한 매트릭스

| 권한 | 뜻 | VIEWER | REQUESTER | APPROVER | MANAGER |
|---|---|:--:|:--:|:--:|:--:|
| `viewDispatch` | 법인 배차 현황 조회 | ● | ● | ● | ● |
| `createRequest` | 배차 요청 생성 | | ● | ● | ● |
| `approve` | 추천 후보 승인/반려 | | | ● | ● |
| `viewBoard` | 차량 × 시간 타임라인 보드 | | | ● | ● |
| `manageMembers` | 멤버 등급 부여/변경 | | | | ● |
| `manageFleet` | 플릿·리스 계약 관리(연장/해지 요청) | | | | ● |
| `manageSettings` | 법인 설정 변경 | | | | ● |

권한은 **누적**이다(상위 등급은 하위 등급의 권한을 모두 갖는다). 다만 이 누적성은
매핑 상수의 성질이지 코드가 강제하는 규칙이 아니다 — 나중에 누적이 아닌 권한이 필요해지면
`CORP_PERMISSIONS` 표만 고치면 되고, 판정 코드는 그대로다.

## 결정 4 — 등급→권한 매핑은 shared 단일 소스에만 있다

`packages/shared/src/corp/grade.ts`의 `CORP_PERMISSIONS`가 유일한 판정 근거다.

```
                      ┌─────────────────────────────────────┐
                      │ shared: CORP_PERMISSIONS            │
                      │        hasCorpPermission(g, p)      │
                      │        minimumGradeFor(p)           │
                      └───────┬─────────────┬───────────────┘
                              │             │
        API 가드 ─────────────┘             └───────── 웹 화면
  CorpPermissionGuard                        BizPermissionGate · 탭/버튼 노출
  @RequireCorpPermission('approve')          hasCorpPermission(user.corpGrade, 'approve')
```

- **가드는 등급표를 다시 적지 않는다.** `corp-permission.guard.ts`는 `hasCorpPermission`만 부른다
- **화면도 다시 적지 않는다.** 탭·버튼 노출과 `BizPermissionGate`가 같은 함수를 부른다.
  권한 없음 안내의 "필요 등급: 관리자" 문구조차 `minimumGradeFor(permission)`가 만든다 —
  문구를 손으로 적으면 등급표를 고쳤을 때 안내와 실제 판정이 갈라진다
- **테스트도 기대값을 적지 않는다.** `test/m5-e2e.int-spec.ts`는 `/biz` 엔드포인트 목록을
  Nest 라우트 메타데이터에서 뽑고, 기대값을 `hasCorpPermission`에서 뽑아 등급 × 엔드포인트를
  전수로 돌린다. 그래서 다음 셋이 전부 테스트 실패로 잡힌다:
  - 권한 데코레이터 없이 `/biz` 엔드포인트를 추가한 경우
  - 등급표를 고치고 가드나 화면을 안 고친 경우
  - 새 엔드포인트를 매트릭스 견본에 넣지 않은 경우

**이유**: 권한은 두 벌이 되는 순간 반드시 어긋난다. 어긋남의 방향이 "화면엔 버튼이 있는데
서버가 403"이면 사용자가 당황할 뿐이지만, 반대 방향이면 그건 보안 사고다. 상수 하나로
모으는 비용(shared 패키지 의존)이 그 위험보다 훨씬 싸다.

## 결정 5 — 등급은 JWT가 아니라 요청마다 DB에서 다시 읽는다

`CorpPermissionGuard`는 토큰에 실린 `corpGrade`를 **믿지 않고** `user` 테이블에서 다시 읽는다.

```
요청 → JwtAuthGuard (토큰 검증, req.user 채움)
     → CorpPermissionGuard
          ├─ prisma.user.findUnique({ id }) → { corporationId, corpGrade }   ← DB 재조회
          ├─ 법인 미소속이면 403
          ├─ hasCorpPermission(corpGrade, 필요 권한) 아니면 403
          └─ req.user.corpGrade := DB 값   (이후 서비스는 최신 등급을 본다)
```

**이유**: 토큰 수명이 7일이다. MANAGER가 누군가의 등급을 낮췄는데 그 사람의 토큰이
살아 있는 동안 옛 권한이 유지되면, 강등은 "최대 7일 뒤에 적용되는 조치"가 된다.
권한 회수는 즉시여야 의미가 있다.

**비용**: 보호된 요청마다 인덱스 조회 1회. 같은 요청에서 서비스가 어차피 유저를 다시 읽는
경우도 있어 완전히 공짜는 아니지만, 이 규모에서 문제가 되는 비용이 아니다.
문제가 될 규모라면 등급을 짧은 TTL 캐시에 두고 등급 변경 시 무효화하는 것이 다음 단계다.

JWT의 `corpGrade`는 버린 것이 아니라 **용도가 다르다** — 웹이 로그인 직후 탭·버튼을
그릴 때 쓰는 값이고, 판정의 근거가 아니다. `jwt-auth.guard.ts`의 `JwtUser` 주석에
그 구분이 적혀 있다.

통합 테스트가 이 결정을 고정한다: 승격 → **같은 토큰으로** 요청 생성 성공,
강등 → **같은 토큰으로** 403 (`test/m5-e2e.int-spec.ts` ⑦).

## 결정 6 — 문서에 없던 계약 변경 2건

M5 작업 문서에는 없었지만 구현하면서 **기존 API의 동작을 바꾼** 것이 둘 있다.
둘 다 되돌릴 수 있는 변경이 아니라 명시적으로 기록해 둔다.

### ① 운영 어드민(OPS_ADMIN)의 `/biz/*` 접근을 차단했다

이전에는 `GET /dispatch/requests/:id`가 OPS_ADMIN에게도 열려 있었다(운영이 법인 배차를
들여다볼 수 있게 한 예외). M5-3에서 이 예외를 제거했다 — 지금은 **OPS_ADMIN도 `/biz` 전 구간 403**이다.

- **근거**: 바운디드 컨텍스트를 나눈 이상 `/biz`는 "법인 고객이 자기 법인을 관리하는 서비스"다.
  운영 도구가 그 안에 예외로 들어와 있으면 경계가 경계가 아니게 된다 —
  추출할 때 "운영도 이 API를 쓰던데" 하는 의존이 반드시 튀어나온다.
  운영이 봐야 할 것은 M3 `/ops` 쪽에서 **자기 경로로** 봐야 한다
  (리스 요청 처리 `/ops/leases`가 그 첫 사례다)
- **트레이드오프**: 지금 당장 운영 어드민이 법인 배차 현황을 볼 방법이 없다.
  M3 백오피스가 붙기 전까지는 공백이다. 대신 그 공백이 "운영용 조회 API를 `/ops`에
  만들어야 한다"는 요구로 남아 있어, 예외 하나로 덮었을 때보다 다음 작업이 분명하다
- **판정 위치**: 이 차단은 가드가 "법인 등급이 없으면 403"으로 처리한다. 즉 OPS_ADMIN을
  이름으로 막는 게 아니라, **등급이 없는 계정은 법인 컨텍스트 밖**이라는 한 규칙의 결과다.
  개인 이용자(`user@demo.mocar.kr`)도 같은 이유로 403이다

### ② `viewDispatch`의 범위를 법인 전체로 통일했다

이전에는 배차 요청 목록이 역할에 따라 범위가 달랐다 — **CORP_MEMBER는 본인 요청만**,
CORP_ADMIN은 법인 전체. 지금은 `viewDispatch` 권한이 있으면 **누구나 법인 전체**를 본다.

- **근거**: VIEWER 등급의 정의가 "배차 현황 조회만 가능"이다. 여기서 '현황'이 사람마다
  다른 범위를 뜻하면 등급 설명이 거짓말이 된다. 그리고 범위를 등급별로 쪼개기 시작하면
  권한 하나(`viewDispatch`)로 판정할 수 없어져, `CORP_PERMISSIONS` 단일 소스(결정 4)가
  깨진다 — 가드는 통과시키고 서비스가 다시 등급을 보고 범위를 좁히는 이중 판정이 된다.
  **판정은 권한 하나로 갈리고, 범위는 테넌시(법인 경계)로만 갈린다**는 규칙을 택했다
- **트레이드오프**: 임직원이 동료의 배차 요청 목적(`purpose`)과 이동 구간을 볼 수 있다.
  법인 차량 이용 현황이 사내에 공개되는 셈인데, 실서비스라면 개인정보 문제가 될 수 있다.
  이 데모에서는 "법인 플릿은 회사 자산이고 그 사용 현황은 회사 안에서 공유된다"로 보고
  감수했다. 필요해지면 **범위를 등급으로 나누는 대신 권한 키를 하나 더 두는 쪽**
  (`viewOwnDispatch` / `viewDispatch`)이 이 설계와 맞다
- 서비스 계층은 `corporationId`만 확인한다. 등급 판정은 가드에서 끝났고, 서비스가 하는 일은
  **다른 법인 침범을 막는 것뿐**이다 (`dispatch.service.list` / `detail`)

## 결정 7 — 전용 차량 = 리스 계약. 계약은 MOCAR가 소유하고 법인은 요청만 한다

M5-1에서 기존 법인 전용 차량(`Vehicle.corporationId`)을 **`LeaseContract`로 백필**했다.
"법인 전용 차량"은 이제 **MOCAR가 그 법인에 리스한 차량**이라는 뜻이고, 월 리스료·계약 기간·
만기가 따라온다. 배차(ADR-003)의 "전용 차량은 이용 과금이 없다"가 여기서 근거를 얻는다 —
과금은 이미 월 리스료로 끝났기 때문이다.

> `LeaseContract`(법인↔MOCAR 계약 = 법인 관점 비용, MOCAR 관점 매출)와
> M3의 `VehicleFinance`(MOCAR 원가 관점 — 차량 매입·보험)는 다른 것이다.
> 스키마 주석에 그 구분을 적어 두었다.

### 상태 전이 — 누가 어떤 상태를 만드는가

```
        ┌──────── biz (법인, manageFleet) ────────┐  ┌──── ops (OPS_ADMIN) ────┐

ACTIVE ──연장 요청──▶ EXTENSION_REQUESTED ──승인──▶ ACTIVE   (endAt := requestedEndAt)
                                          └─반려──▶ ACTIVE   (requestNote := "반려: …")

ACTIVE ──해지 요청──▶ TERMINATION_REQUESTED ─승인──▶ ENDED    (endedAt := now)
                                            └반려──▶ ACTIVE

ENDED  ──(요청 불가, 409)
```

**법인은 `*_REQUESTED`만, 운영은 `ACTIVE`/`ENDED`만 만든다.** 법인이 스스로 만기를 옮길 수
있으면 그건 계약이 아니라 설정이다. 그래서 계약의 소유권은 MOCAR(운영) 쪽에 두고, 법인 쪽
API는 상태를 "처리 대기"로 올리는 것까지만 한다.

- 처리 대기 중 재요청 · 종료된 계약 재요청 · 이미 처리된 요청 재처리는 **모두 409**
  ("상태가 맞지 않아 처리할 수 없음"을 한 코드로 통일)
- 반려 사유는 전용 컬럼 없이 `requestNote`에 `반려: …`로 남긴다
  (M5는 마이그레이션 1건으로 닫기로 했고, 계약의 "최근 메모" 필드를 재사용해도 손해가 없다)
- **해지 승인 시 차량 회수(REPOSITION) 작업 생성은 M2 완료 후**다. 지금은 계약 상태만 바꾸고
  `Vehicle.corporationId`는 건드리지 않는다 — 즉시 회수하면 이미 잡힌 배차·예약이 깨진다
- 응답 DTO 매핑은 biz와 ops가 **공유하지 않는다**. 계산(D-day·이용률)은 shared 순수 함수를
  같이 쓰되, DTO 조립은 각 컨텍스트가 자기 것을 갖는다 — 두 컨텍스트를 떼어낼 때
  잘라내는 선이 바로 여기라서

## 예약된 권한 — `manageSettings`

`CORP_PERMISSIONS`의 7개 권한 중 `manageSettings`(법인 설정 변경)만 **정의만 있고 쓰는
엔드포인트가 없다.** 지울 수도 있었지만 남겨 두었다 — 등급 설명("MANAGER: 멤버 등급 ·
플릿/리스 · 법인 설정 관리")과 화면 안내가 이미 이 개념을 말하고 있고, 법인 설정
(오피스 위치·기본 승인자·예산 한도 같은 것)은 이 도메인에서 자연스럽게 다음에 올 기능이다.

미사용이라는 사실 자체를 테스트가 지킨다: `test/m5-e2e.int-spec.ts`가 라우트 메타데이터에서
실제로 쓰이는 권한을 모으고, **쓰이지 않는 권한 집합이 `['manageSettings']`와 정확히
같은지** 단언한다. 다른 권한이 조용히 미사용이 되면 실패하고, `manageSettings`에
엔드포인트가 붙는 순간에도 실패한다(그때 이 목록에서 지우면 된다).

  라우트 메타데이터에서, 기대값은 `CORP_PERMISSIONS`에서 나온다 — 매트릭스를 손으로 적은
  자리가 없다
- **경계 검사**: 운영 어드민 · 법인 미소속 개인은 `/biz` 전 엔드포인트 403, 미인증은 401,
  법인 MANAGER는 `/ops/leases` 403 — 양방향으로 막혀 있다
- **동선 완주**: VIEWER(조회만) → REQUESTER(요청) → APPROVER(승인, Role은 임직원) →
  MANAGER(등급 변경·플릿·리스 연장 요청) → ops(승인, 만기 이동) → 해지까지 한 법인이
  등급대로 완주한다 (`test/m5-e2e.int-spec.ts` 동선 완주 12단계)
- **즉시 반영**: 등급 승격·강등이 토큰 재발급 없이 다음 요청부터 적용된다
