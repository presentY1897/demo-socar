# ADR-002. 결제 멱등성과 트랜잭션 경계

## 상황

결제는 "정확히 한 번"이 지켜져야 한다. 위험 지점 두 곳:

1. **예약 결제**: 사용자의 더블 클릭, 네트워크 타임아웃 후 재시도 → 중복 과금
2. **반납 정산**: 정산 요청이 실패한 뒤 재시도 → 주행요금 이중 청구

## 결정

### 멱등성 키

- 클라이언트가 예약 시도마다 UUID 멱등성 키를 생성해 전송, `Payment.idempotencyKey`는 UNIQUE
- 같은 키 재요청: 이미 CAPTURED면 기존 결제를 그대로 반환 (재과금 없음)
- 같은 키를 **다른 예약**에 재사용하면 400으로 거절 — 키 오염 방지
- 반납 정산 키는 서버가 `settle-{rentalId}`로 고정 생성 → 정산은 몇 번을 재시도해도 1회만 청구

### 트랜잭션 경계

예약 생성 · 쿠폰 사용 · 크레딧 차감 · 결제를 **하나의 DB 트랜잭션**으로 묶는다.
카드 승인 거절(모의 PG: `0000` 카드) 시 전체가 롤백되어 "결제는 실패했는데 예약은 잡혀 있는"
상태가 존재하지 않는다.

### 상태 머신

```
Payment: PENDING → CAPTURED → REFUNDED
                 ↘ FAILED
Rental:  IN_USE → RETURN_PENDING → COMPLETED
```

반납 정산이 실패하면 Rental은 `RETURN_PENDING`에 머물고, 사용자는 정산만 재시도한다.
차량 반납 사실과 돈 문제를 분리해 상태가 꼬이지 않게 했다.

### 예약 변경·연장의 차액 처리

- 시간 변경/연장으로 금액이 **늘면** 차액만 추가 결제한다 (새 멱등성 키)
- 금액이 **줄면** 모의 PG에 부분 환불이 없으므로 **크레딧으로 환급**한다 —
  실제 PG라면 부분 취소 API를 쓰는 자리라는 것을 인지한 단순화다
- 이용 중 연장은 뒤 예약과의 충돌을 사전 확인하고, 최종적으로는 ADR-001의
  EXCLUDE 제약이 update 시점에 다시 방어한다

## 실제 PG 연동 시 달라질 것 (인지하고 있는 한계)

- 실제 PG는 외부 시스템이라 DB 트랜잭션에 넣을 수 없다 → 승인/캡처 2단계 + 보상 트랜잭션
  (실패 시 취소 API) + 웹훅 기반 최종 상태 동기화로 재설계해야 한다
- 이 데모의 모의 PG는 그 상태 머신과 멱등성 계약을 동일하게 유지한 채 경계만 단순화한 것
