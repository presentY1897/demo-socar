# ADR-007. 체크인/체크아웃 게이트와 가상 스마트키 상태 머신

## 상황

카셰어링에는 대면 인수인계가 없다. 그래서 "받았을 때 이미 있던 흠집"과 "내가 낸 흠집"을
가를 증거가 이용 시작 시점에 남지 않으면, 분쟁은 언제나 다음 이용자에게 떠넘겨진다.
반대로 반납 시점에 차를 어디에 어떻게 세웠는지가 남지 않으면 다음 이용자가 지하 3층에서
차를 찾아 헤맨다.

M1은 여기에 두 개의 확인 절차(체크인·체크아웃)와 가상 스마트키를 넣는다. 결정해야 했던 것:

1. 확인 절차를 **권고**로 둘 것인가 **관문**으로 둘 것인가 — 강제하면 증거는 남지만 이용 마찰이 는다
2. 가상 스마트키의 범위 — 실물 쏘카 스마트키에는 없는 **시동**을 넣을 것인가
3. 조작의 정합성 규칙을 어디에 두고, 거절된 조작을 어떻게 다룰 것인가
4. 증빙 사진을 어디에 저장할 것인가

## 결정 1 — 체크인을 스마트키의 활성화 조건으로 둔다

```
Rental(IN_USE) ──체크인 미완료──▶ POST /rentals/:id/control  → 403
Rental(IN_USE) ──체크인 완료────▶ POST /rentals/:id/control  → 201
Rental(IN_USE) ──체크아웃 미완료─▶ POST /rentals/:id/return   → 409
```

**증거를 남기는 시점은 "차를 쓰기 직전"밖에 없다.** 이용이 끝난 뒤에 촬영을 요구하면
그 사진은 이미 이용 후의 차량 상태라 인수 시점의 증거가 되지 못한다. 그래서 체크인을
권고 배너가 아니라 스마트키의 **선행 조건**으로 두었다 — 차 문을 열려면 반드시 통과한다.

마찰을 그 대가로 치르되, 마찰이 커지는 지점은 깎았다:

- 체크인은 **사진 1장 + 선택 메모**면 통과한다. 항목별 체크리스트를 요구하지 않는다
- 사진은 촬영 즉시 클라이언트에서 압축한다 — 제출 버튼에서 몰아 처리하면 멈춘 것처럼 보인다
- 화면은 `GET /rentals/:id/usage` 하나로 현재 단계를 판정하고 **그 단계의 화면 하나만** 그린다
  (체크인 → 이용 중·스마트키 → 체크아웃 → 반납). 처음에는 다섯 단계 카드를 한 페이지에 늘어놓고
  잠긴 카드를 흐리게만 했는데, 차 앞에 선 사람에게는 "지금 할 일 하나"만 보이는 편이 맞았다.
  끝난 단계는 "기록 보기"로 접어 두고, 이용 중에는 홈도 지도 대신 이 화면이다
- 게이트는 이용 시작(`/rentals/start`)이 아니라 **스마트키**에 건다. 대여는 이미 열려 있고,
  체크인은 차를 여는 마지막 한 단계라 "예약은 됐는데 못 들어간다"는 느낌이 들지 않는다

체크아웃은 같은 논리를 반납 쪽에 적용한 것이다. 반납은 **돈이 정산되는 비가역 행위**라
그 앞에 주차 위치 증빙을 세웠다.

**상태 코드를 나눈 이유**: 게이트 위반은 403(조건을 아직 충족하지 못함), 순서·중복 위반은
409(현재 상태와 충돌), 페이로드 위반은 400이다. 클라이언트가 "다시 시도하면 되는 것"과
"앞 단계를 먼저 해야 하는 것"을 코드만 보고 가른다.

## 결정 2 — 가상 스마트키에 시동(IGNITION_ON/OFF)을 포함한다

**실물 쏘카 스마트키에는 시동 기능이 없다.** 실차의 스마트키는 문 열기/잠금, 비상등, 경적까지고,
시동은 차 안의 스마트키 카드/버튼으로 건다. 안전 때문이다 — 앱으로 원격 시동이 걸리면
차 주변에 사람이 있는지 앱이 알 수 없다.

그럼에도 이 데모는 시동을 포함한다.

- **데모의 목적이 다르다.** 이 프로젝트가 보여주려는 건 "차량 제어 명령이 상태 머신을 통과해
  로그로 남는 경로"다. 문 잠금만 있으면 상태가 불리언 하나라 상태 머신이라 할 것이 없다.
  시동이 들어오는 순간 **두 상태가 서로를 제약**하고, 그때부터 정합성 규칙이 의미를 갖는다
- **이용 플로우가 완결된다.** 체크인 → 문 열기 → 시동 → 주행 → 시동 끄기 → 잠금 → 체크아웃까지
  이어져야 "이용"이 하나의 이야기가 된다. 시동이 빠지면 문만 여닫는 리모컨 데모가 된다
- 안전 문제는 **실차가 없어서** 성립하지 않는다. 이 결정은 모의 환경에 한정된 것이고,
  실차 연동이라면 원격 시동은 넣지 않았을 것이다

> 이 결정은 work-plan Q3(2026-09-01)에서 "시동 포함"으로 확정됐고,
> `packages/shared/src/schemas/control.ts` 주석에도 같은 내용이 붙어 있다.

## 결정 3 — 상태 머신은 shared의 순수 함수 하나가 유일한 근거

차량 상태는 `doorLocked × engineOn` 두 불리언이다. 네 조합 중 **셋만 도달 가능**하다.

```
   (잠김·시동OFF) ──UNLOCK──▶ (열림·시동OFF) ──IGNITION_ON──▶ (열림·시동ON)
        ▲                          │   ▲                          │
        └────────LOCK──────────────┘   └──────IGNITION_OFF────────┘

   (잠김·시동ON) — 도달 불가능한 상태
```

| 조작 | 허용 조건 | 거절 시 | 이유 |
|---|---|---|---|
| `UNLOCK` | 항상 | — | 이미 열린 문을 다시 여는 것도 실물 리모컨처럼 통과시킨다 |
| `LOCK` | 시동 OFF | 400 | 시동이 걸린 채 잠그면 차 안에 키를 두고 잠그는 상황이 된다 |
| `IGNITION_ON` | 문 열림 | 400 | 문이 잠긴 채 시동이 걸리면 아무도 탈 수 없는 상태가 만들어진다 |
| `IGNITION_OFF` | 항상 | — | 안전한 방향의 조작은 막지 않는다 |
| `HAZARD` · `HORN` | 항상 | — | 신호일 뿐이라 상태를 바꾸지 않는다 |

두 금지 규칙은 짝이다 — 하나만 넣으면 `(잠김·시동ON)`이 도달 가능해진다.

규칙은 `packages/shared/src/schemas/control.ts`의 순수 함수 `applyControl(state, action)`에만
있고, **서버 검증과 화면의 버튼 활성 조건·낙관적 갱신이 같은 함수를 호출한다.** 규칙이 두 벌이면
"버튼은 눌리는데 서버가 거절"하거나 그 반대인 어긋남이 반드시 생긴다. 그래서 화면은 불가능한
조작을 아예 비활성화하고(사유는 `title`), 롤백은 **실제 실패(네트워크·권한·경합)** 에만 쓴다.

### 거절된 조작은 로그에 남기지 않는다

`VehicleControlLog`는 **차에 실제로 일어난 일**의 기록이다. 거절된 요청은 차에 아무 일도
일으키지 않았으므로 이 로그에 들어가면 안 된다 — 사고 조사나 배차 이력에서 "이 시각에 시동이
걸렸는가"를 물을 때, 거절된 시도가 섞인 로그는 답을 줄 수 없다.

거절 자체를 관측하고 싶다면 그건 **다른 종류의 데이터**(애플리케이션 로그·감사 로그)다.
차량 상태 이력과 요청 이력을 한 테이블에 섞지 않는다.

## 결정 4 — ConditionReport "단계별 1건"은 DB 유니크가 아니라 API 정책

`(rentalId, phase)` 유니크 제약을 넣지 않았다. 대신 API가 중복 제출을 409로 막고,
**조회는 항상 "단계별 최신 1건"**(`orderBy: createdAt desc`)을 유효 보고로 본다.

- M1의 스키마 변경은 M1-1 한 건으로 닫기로 정했다. 유니크 제약을 위해 마이그레이션을 하나 더
  추가하면서 얻는 건 **이미 API가 막고 있는 규칙의 이중화**뿐이다
- 재제출을 열어줄 여지를 남긴다. 사진을 잘못 찍었거나 운영자가 대리 등록해야 하는 상황은
  실제로 생기는데, DB 유니크는 그 순간 또 마이그레이션을 강제한다.
  지금 구조에서는 `latestReport`가 그대로고 컨트롤러의 409만 걷어내면 된다
- 지금 정책은 **재제출 불가(409)**. 잘못 올린 사진은 운영 문의(M1-7)로 처리한다

동시성 관점의 정당화도 필요하다: 이 규칙은 **한 사용자가 자기 대여에 대해** 지키는 것이라
동시 요청 경합의 위험이 예약 겹침(ADR-001)과 같지 않다. 중복 제출은 최악의 경우 같은 단계의
보고가 2건 쌓이는 것이고, 조회 규칙이 최신 1건이라 화면과 게이트는 흔들리지 않는다.
돈이나 재고가 걸린 규칙이었다면 DB 제약으로 내렸을 것이다.

> 이 판단의 원문 근거는 [`docs/task/m1-3-checkin-checkout.md`](../task/m1-3-checkin-checkout.md)
> "열린 질문 해소" 절에 있다.

## 결정 5 — 사진은 외부 스토리지 대신 압축 base64로 DB에 넣는다

체크인/체크아웃/사고 접수의 사진을 S3·Cloudinary 같은 외부 스토리지가 아니라
`ConditionPhoto`/`IncidentPhoto` 테이블의 base64 텍스트 컬럼에 저장한다.

**이유**: 이 데모는 전 구간을 무료 티어로 유지한다(Vercel + Render + Neon). 스토리지를
하나 더 붙이면 계정·키 관리·CORS·서명 URL 만료가 따라오는데, 그건 이 프로젝트가 보여주려는
문제(이용 플로우의 상태 머신)와 아무 상관이 없는 복잡도다. 대신 **용량 상한을 계약으로 못 박아**
DB가 감당할 수 있는 크기로 눌렀다:

- 클라이언트에서 최대 변 1280px 리사이즈 → JPEG 품질 0.7/0.55/0.4/0.3 순으로 낮추며
  200KB 이하가 되는 첫 결과를 채택 (`apps/web/src/lib/image.ts`)
- 장당 200KB · 건당 5장 = **접수 1건당 최대 1MB** (`packages/shared/src/schemas/photo.ts`)
- 웹의 압축 목표치와 API의 검증 상한이 **같은 파일의 같은 상수**다 — 어긋날 수가 없다
- 서버는 클라이언트가 보낸 `bytes`를 믿지 않고 다시 계산해서 저장한다
- 응답은 `data:` URI로 내려간다 → 정적 파일 서빙 경로도, 서명 URL도 필요 없다

### 알고 있는 한계

- **행이 무겁다.** base64는 원본의 약 1.33배라 1MB 접수가 DB에서는 ~1.3MB다.
  Postgres TOAST가 압축해 주지만 JPEG는 이미 압축돼 있어 이득이 거의 없다
- **백업·덤프가 같이 커진다.** 사진은 한번 쌓이면 줄지 않는데 DB 덤프에 그대로 따라붙는다.
  무료 티어 용량(Neon 0.5GB)이 사실상 사진 예산의 상한이다
- **CDN 캐시를 못 쓴다.** 사진이 API 응답 본문에 실려 오므로 이미지 캐싱·리사이즈·지연 로딩
  같은 걸 브라우저/CDN에 맡길 수 없다. 목록 화면에서 사진을 많이 그리기 시작하면 이게 먼저 아프다
- **원본을 보관하지 못한다.** 분쟁 증거로서는 1280px/200KB가 아쉬울 수 있다.
  실서비스라면 원본을 스토리지에, 썸네일만 DB에 두는 형태가 맞다

전환 지점은 좁게 설계해 뒀다: `apps/api/src/photos/photo-storage.ts`의
`toPhotoRows`(저장) / `toStoredPhotos`(응답) 두 함수만 URL 기반으로 바꾸면 되고,
`ConditionPhoto`와 `IncidentPhoto`가 같은 컬럼 규격이라 두 테이블이 함께 옮겨간다.

## 결과

- 통합 테스트로 고정한 게이트: 체크인 전 `control` → 403(로그·차량 상태 불변),
  체크인 전 체크아웃 → 409, 체크아웃 전 `return` → 409, 중복 제출 → 409, 남의 대여 → 403
- 정합성: 시동 ON 중 `LOCK` → 400, 문 잠긴 채 `IGNITION_ON` → 400, **거절된 조작은 로그에 없음**
- `test/m1-e2e.int-spec.ts`가 예약 생성 → 변경 → 체크인 → 스마트키 → 매뉴얼 → 연장 →
  체크아웃 → 반납·정산까지 한 예약으로 완주하며 위 게이트를 동선 안에서 다시 확인한다
- `Vehicle.doorLocked`/`engineOn`은 M3-1에서 `VehicleTelemetry`로 통합될 임시 필드다.
  그때 상태 머신(`applyControl`)은 그대로 두고 상태의 저장 위치만 옮긴다
  → **M3-1에서 예고대로 이관 완료.** 응답 계약(`SmartKeyStateRes`)이 그대로라 화면은 무변경
  ([ADR-009](009-ops-backoffice-telemetry.md) 결정 4)
